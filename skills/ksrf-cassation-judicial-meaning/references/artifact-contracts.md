Все изменяемые данные конкретного дела лежат в выбранном пользователем workspace, а не в каталоге установленного скилла. Повторно используемый публичный кеш имеет отдельный root и никогда не принимает applicant-private artifacts.

## 1. Артефакты дела и поиска

| Артефакт | Назначение | Gate |
|---|---|---|
| `intake/applicant-private.jsonl` | Локальный извлечённый текст и private provenance актов заявителя | fingerprint |
| `intake/applicant-manifest.jsonl` | Публично безопасные хеши, роли и extraction status | fingerprint |
| `applicant-chain.json` | Стадии, факты, нормы, speakers, исходы и неясности | plan freeze |
| `case-fingerprint.json` | Текущая ревизия нейтрального вопроса, норм и признаков | case-relative review |
| `casework/fingerprints/fingerprint-vN.json` | Неизменяемая история fingerprint | stale audit |
| `casework-dependencies.json` | Missing tasks и состояние зависимых applicant-relative артефактов | comparability |
| `query-suggestions.jsonl` | `suggested_unconfirmed` запросы с reason codes и provenance | query review |
| `query-decisions.jsonl` | Принятые человеком `accepted_pre_freeze` запросы | plan freeze |
| `supplemental-queries.jsonl` | Раскрытые `post_freeze_supplemental`, не меняющие исходный знаменатель | evidence review |
| `research-plan.json` | Редактируемый шаблон Evidence Acquisition Plan | plan freeze |
| `plans/plan-vN.json` | Неизменяемый план и SHA-256 | collection |
| `research-questions.jsonl` | Только neutral questions/hypotheses under test | collection |
| `queries.jsonl` | Исполняемые обычные, adverse и supplemental дорожки | collection |
| `run.json` | Текущий `run_id`, `plan_sha256` и runtime binding | collection |

`intake` создаёт `applicant-chain.json` с `run_id=null`: исследовательский запуск ещё не существует. Первый `collect` создаёт `run_id` и атомарно привязывает chain к нему. `case prepare` до intake запрещён.

Принятые до freeze query suggestions копируются в замораживаемый план и входят в `plan_sha256`. После freeze новый поиск записывается как supplemental с `changes_original_denominator=false`; он не переопределяет совокупность задним числом.

## 2. Артефакты корпуса

| Артефакт | Назначение | Gate |
|---|---|---|
| `corpus.sqlite3` | Транзакционный источник collection state | после freeze |
| `exports/coverage.json` | Страницы, terminal states, denominator и пробелы по режиму/суду/дате | coverage review |
| `exports/sources.jsonl` | Official URLs, raw/text hashes и provenance | coding |
| `exports/case-chains.jsonl` | Независимые цепочки и merge/split review | analysis |
| `screening-candidates.jsonl` | Все кандидаты по замороженным дорожкам | coding |
| `coding-decisions.jsonl` | Полнотекстовые юридические коды, speaker, цитаты и решения об исключении | adverse review |
| `adverse-review.json` | Общий corpus adverse-pass | analysis |
| `analysis.json` | Независимые цепочки, временные матрицы, denominator scope и предел вывода | thesis review |
| `thesis-candidates.jsonl` | Только post-corpus кандидаты | thesis review |

Каждый screening candidate разрешается по паре `chain_id + document_id`: одобренная полнотекстовая позиция либо одобренное полнотекстовое исключение. Пока `screening_resolution_complete=false`, evidence review и `drafting_ready` блокируются.

`quality coding-audit-prepare` читает готовые артефакты корпуса, проверяет идентичность по содержимому всех захваченных текстов до фильтрации по запросам и одним переименованием публикует отдельный неизменяемый каталог первичных входов аудита контракта `1.2`. Обязательный `--codebook-version 1.0` выбирает штатный справочник независимо от ответов первого кодировщика и должен точно совпасть с версией во всех первичных карточках. Команда не изменяет рабочую папку и не принимает существующий каталог назначения; родитель результата должен принадлежать текущему эффективному пользователю и быть закрыт от записи группы и других пользователей. Владелец и режим родителя проверяются при открытии, непосредственно перед переносом и при окончательном подтверждении. Состав пакета ограничивается до чтения всех файлов; до создания ZIP проверяются пределы каждого участника и всей полезной нагрузки, а ZIP создаётся с запретом ZIP64 (`allowZip64=false`). В трёх штатных файлах идентичности `document_id` имеет точную форму `document-sha256:<64 строчные шестнадцатеричные цифры>`.

На macOS одних режимов `0700`/`0600` недостаточно: у родителя, временной и итоговой папок и каждого созданного файла не должно быть вообще никакого расширенного ACL. Родитель проверяется при каждой повторной проверке, временная папка — до файлов, каждый файл — до первого байта, итоговая папка и файлы — до и после переноса. Запрещающие (`deny-only`) и ненаследуемые записи ACL тоже отклоняются, а ошибка системной ACL-проверки или невозможность подтвердить неизменность файловой идентичности блокирует публикацию. Это правило относится к macOS и не заявляет проверку ACL в Linux. Пользователь выбирает приватный родитель без расширенного ACL или обращается к системному администратору; один `chmod` не удаляет и не доказывает отсутствие ACL. Сбой после создания временной папки следует аварийному контракту сохранения и карантина ниже.

| Артефакт пакета аудита | Назначение | Этап проверки |
|---|---|---|
| `screening-candidates.audit.jsonl` | Закрытая рамка с производными ID кандидатов, SHA плана, ID источников и повторно проверенными совпадениями | формирование выборки |
| `primary-decisions.audit.jsonl` | Точные 20-полевые карточки первичной разметки, повторно сверенные с сохранённым полным текстом | независимая проверка |
| `coding-audit-plan.json` | Две независимо ранжированные максимальные выборки; они могут пересекаться | независимая проверка |
| `secondary-review-queue.jsonl` | Идентичность и хеши содержимого без содержательных ответов первого кодировщика | ручная вторичная разметка |
| `secondary-coding-template.jsonl` | Намеренно незавершённые шаблоны со статусом `pending` | ручная вторичная разметка |
| `independent-review-packet.zip` | Единственный передаваемый второму кодировщику файл; ровно пять файлов содержимого (`CODING-BRIEF.json`, файл штатного справочника, файл инструкции для проверяющего, `review-materials.jsonl`, `secondary-coding-template.jsonl`) и `review-packet-manifest.json` без первичной разметки | независимая проверка и сверка SHA-256 |
| `coding-audit-inputs-manifest.json` | Версия `1.2`, SHA исходных данных и каждого файла пакета, полная рамка и обязательная выборка; одобрение и юридическая готовность всегда `false` | целостность и внешняя привязка |

Весь каталог является пакетом хранителя и содержит первичные ответы: передавать его независимому кодировщику нельзя. Передаётся только `independent-review-packet.zip`. `quality coding-audit-prepare` выводит две отдельно сохраняемые контрольные суммы: `manifest_sha256` нужен хранителю для последующего импорта, а `independent_review_packet_sha256` хранитель сообщает проверяющему по независимому каналу, отдельно от ZIP. Проверяющий сверяет SHA-256 полученного архива до распаковки.

`CODING-BRIEF.json` переносит из замороженного плана только нейтральный контекст, нужный для разметки: ровно одну направленную гипотезу `hypothesis_under_test`, нормы, совокупность и правила включения, исключения, исходозначимости и противоречия. Файл инструкции для проверяющего версии `1.2` использует русские пояснения: «пакет аудита», `reading_family` («семейство толкования»), `supports` («поддерживает») и `adverse` («противоречит»). Имена JSON-поля и значений остаются точными английскими идентификаторами, а `supports` и `adverse` относятся к направленной гипотезе; открытый вопрос или несколько гипотез требуют отдельных заново замороженных планов. Файл постановки задания не содержит поисковых запросов, совпадений или ответов первого кодировщика. Файл «CODING-CODEBOOK.md» фиксирует штатную процедуру выбранной версии; внутренний манифест связывает точные байты и SHA-256 обоих файлов. После обновления инструкции новый запуск подготовки создаёт новые неизменяемые байты ZIP и связанные контрольные суммы: используй `independent_review_packet_sha256` и `manifest_sha256` только от этого же запуска, не исправляй ZIP вручную и не подставляй суммы прежнего пакета.

Ослепление структурное и ограниченное: первичная разметка и её хеши, имя первого кодировщика, текст поисковых запросов, совпадения, метка дорожки отбора (`sample_lane`) и разрешения расхождений не сериализованы внутри ZIP в открытом виде. Полный текст судебного акта и принадлежность к объединённой выборке остаются видимыми, поэтому факты, мотивировка и исход известны; это не оценка с сокрытием исхода (`outcome-blind`). Для нового пакета `1.2` до передачи ZIP хранитель процедурно выбирает и сохраняет псевдонимную метку второго кодировщика, сообщает её отдельно и не использует реальное имя; это значение позже передаётся в `--expected-secondary-coder`. Программа связывает хеш нормализованной метки с квитанцией, но не доказывает момент выбора (`secondary_coder_label_precommit_verified=false`). Внутренний манифест фиксирует `publication_safe=false`, `review_state="independent_secondary_required"`, `human_approval_created=false` и `legal_readiness=false`. Архив требует адресной защищённой передачи и отдельного решения о публикации или редактировании полного текста.

`plan_sha256` и производный `candidate_id` остаются непрозрачной криптографической привязкой к полному замороженному плану, включая поисковые дорожки. Сырые запросы и совпадения не сериализуются, но контрольная сумма не является обещанием семантической тайны для того, кто знает план или способен перебрать его варианты.

После возврата отдельного завершённого JSONL хранитель создаёт совместимые решения аудита штатным импортом:

```bash
KSRF_SKILLS_ROOT="${KSRF_SKILLS_ROOT:-${CODEX_HOME:-$HOME/.codex}/skills}"
JM="$KSRF_SKILLS_ROOT/ksrf-cassation-judicial-meaning/scripts/judicial_meaning.py"
AUDIT_BUNDLE="./coding-audit-inputs"
EXPECTED_MANIFEST_SHA256="<manifest_sha256 из сохранённого стандартного вывода>"
EXPECTED_SECONDARY_CODER="secondary-reviewer"

python3 "$JM" quality coding-audit-review-import \
  --bundle "$AUDIT_BUNDLE" \
  --expected-manifest-sha256 "$EXPECTED_MANIFEST_SHA256" \
  --expected-secondary-coder "$EXPECTED_SECONDARY_CODER" \
  --secondary-coding ./secondary-coding.completed.jsonl \
  --output-dir ./coding-audit-review-import
```

`EXPECTED_MANIFEST_SHA256` берётся из отдельно сохранённого `manifest_sha256` успешной подготовки, не из пакета в момент импорта. Новый импорт принимает пакет `1.2` и пакет версии `1.1` из выпуска 14, привязанный отдельно сохранённым SHA-256; если стандартный вывод выпуска 14 утрачен, этот SHA нельзя восстанавливать из пакета — нужно заново подготовить `1.2` из исходной неизменной рабочей папки или перейти на документированный ручной путь. Для уже возвращённого `1.1` ожидаемая метка лишь проверяет единообразие имеющейся строки, а предварительный выбор псевдонима не доказан. Прежний пятифайловый вариант без `bundle_contract_version` остаётся на ручном пути совместимости. Пакет хранителя и возвращённый файл не изменяются, ZIP проверяется без извлечения на диск, а `--output-dir` должен быть новой соседней папкой рядом с пакетом. Родитель должен принадлежать текущему эффективному пользователю и оставаться закрытым от записи группы и других пользователей при начальной, предпереносной и окончательной проверке. На macOS для импорта действует та же проверка полного отсутствия расширенного ACL у родителя, временной и итоговой папок и каждого созданного файла; режимы `0700`/`0600` сами по себе недостаточны, а сбой после создания временной папки сохраняет возможные объекты для карантина.

До создания временной папки ошибка даёт код `2`, пустой stdout и не создаёт выходных объектов. После успешного `mkdir` любая ошибка до точки фиксации даёт код `2` с пустым stdout и сохраняет временную папку и всё, что могло в ней появиться. Автоматические `unlink` и `rmdir` не выполняются, потому что при конкурентной подмене имени нельзя переносимо и атомарно доказать, что удаляется именно созданный объект.

Точка фиксации — само атомарное перенесение без замены, а не возврат помощника. Идентичность временной папки фиксируется сразу после безопасного открытия и до `fchmod`; при отказе открытия она явно отмечается как неизвестная. Дескрипторы и `st_dev`/`st_ino` созданных файлов удерживаются до классификации сбоя. Если после ошибки помощника итоговое имя доказанно ведёт к снятому inode временной папки, каталог сохраняется как опубликованный результат с неподтверждённым состоянием. Во всех иных случаях после `mkdir` ничего не удаляется и сообщается неподтверждённая очистка.

Обе аварийные ветки дают код `2` с пустым stdout, запрещают повтор и передачу и требуют сохранить входы неизменными. Диагностика сообщает идентичность удерживаемого родителя, прежнее временное имя, известную идентичность временной папки и каждого созданного файла; при отказе открытия идентичность папки указана как неизвестная. Пользователь передаёт системному администратору всю строку ошибки; штатной команды самостоятельного восстановления нет. Администратор находит временную папку и каждый созданный inode по этим координатам, учитывает все имена и жёсткие ссылки каждого файла и помещает каждую найденную копию в карантин. Если каталог, хотя бы один inode или все его ссылки нельзя полностью учесть, считается, что чувствительная копия осталась неучтённой. Состязательные сценарии проверяют отказы открытия/изменения режима, подмену имени, внешнюю жёсткую ссылку, отказ синхронизации и запрет автоудаления.

После переноса код `2` с пустым стандартным выводом требует различать две ситуации. Только если повторно подтверждены эффективный владелец и режим родителя, прежняя запись результата, точный состав, режим `0700` каталога, а на macOS ещё и отсутствие расширенного ACL, а также тип, единственная жёсткая ссылка, режим `0600`, размер и байты каждого файла, но не удалась лишь синхронизация (`fsync`) родителя, входы оставляются неизменными, а результат не передаётся; после восстановления файловой системы импорт повторяется в новую отсутствующую соседнюю папку и оба результата сравниваются побайтно. Изменение владельца или разрешений родителя, перемещение либо замена записи результата, неожиданный состав, режим, число жёстких ссылок, размер, ACL или байты файла означают неподтверждённое состояние публикации. Автоматика останавливается без повтора, удаления или передачи, а входы сохраняются неизменными. Диагностика сообщает координаты удерживаемого родителя, прежнее имя записи, опубликованного каталога и каждого известного созданного файла. Пользователь передаёт всю строку ошибки системному администратору, который находит каталог и каждый созданный inode, учитывает все имена и жёсткие ссылки каждого файла и помещает каждую найденную копию в карантин. Если каталог, хотя бы один inode или все его ссылки нельзя полностью учесть, чувствительная копия считается неучтённой.

После полной публикации с начала передачи финального JSON-подтверждения и до успешного возврата команды любая ошибка или прерывание относится к отдельному сбою доставки. Это включает неполный или неудачный `write`, отказ явного `flush` и прерывание уже после полной записи и успешного `flush`. Каталог сохраняется, код равен `2`, а пустой, частичный или даже выглядящий полным стандартный вывод всегда недействителен и не разбирается. Автоматика останавливается; первый каталог не используется, а команда не повторяется в ту же папку. После восстановления stdout те же неизменные входы публикуются в другую отсутствующую соседнюю папку, одна полная строка JSON успешно записывается и сбрасывается с успешным возвратом команды, а два каталога сравниваются побайтно. Для подготовки оба хеша берутся только из успешного повторного stdout, без восстановления внешнего `manifest_sha256` из первого пакета. Для импорта контрольная сумма квитанции, флаги дальнейших действий и карты различий берутся только из успешного повторного stdout после совпадения каталогов. Состязательные сценарии отдельно проверяют полную, короткую и несброшенную запись, закрытую трубу stdout и прерывание после полного подтверждения.

Любая ошибка или прерывание после публикации, но до начала передачи подтверждения, — отдельная неопределённая финализация. Сюда входят отказ закрытия удерживаемого дескриптора созданного файла, опубликованного каталога или родителя и прерывание оболочки после возврата внутреннего издателя либо после закрытия родителя, но до входа в доставку. Подтверждение ещё не формировалось, поэтому stdout должен быть пустым; код `2` не доказывает отсутствия каталога, а сама эта ветка не должна называться подтверждением долговечности. Входы и найденный каталог сохраняются неизменными и не используются; после устранения системной ошибки команда повторяется с теми же входами в новую отсутствующую соседнюю папку, каталоги сравниваются побайтно, а хеши или квитанция с флагами берутся только из успешного повторного stdout. Отдельные состязательные сценарии проверяют закрытие родителя и дескрипторов файла/каталога, прерывание после возврата внутреннего издателя и прерывание непосредственно перед доставкой.

| Артефакт импорта | Назначение | Граница |
|---|---|---|
| `audit-decisions.jsonl` | Канонические четырёхполевые решения для `quality coding-reliability` | не разрешение расхождений |
| `coding-audit-review-import-receipt.json` | Точные контрольные суммы, узкие группы согласия/расхождения и флаги выполненных проверок | не аутентификация и не юридический допуск |

После штатной финализации появляется отдельный приватный каталог:

| Артефакт финализации | Назначение | Граница |
|---|---|---|
| `resolved-review-decisions.jsonl` | Итоговые записи, детерминированно выведенные из первичных, вторичных и выбранных значений | не подтверждение истинности выбора |
| `adjudications.jsonl` | Совместимые решения ровно по восьми аудируемым полям | декларация, а не аутентифицированный акт |
| `coding-reliability.json` | Повторный расчёт надёжности по тому же связанному состоянию | не юридическая готовность |
| `coding-audit-finalization-receipt.json` | Value-free связи, контрольные суммы и узкие флаги завершения | не подпись, не публикационный или filing-допуск |

Успешный каталог имеет режим `0700`, а файлы — `0600`; владелец каждого созданного объекта повторно проверяется до и после публикации, а на macOS приватность дополнительно требует подтверждённого отсутствия любого расширенного ACL у родителя, итоговой папки и файлов. Квитанция не содержит текст пакета, цитаты или абсолютные входные пути. `returned_quote_literal_presence_verified=true` означает только буквальное присутствие возвращённых основных и альтернативных цитат в связанном тексте; `secondary_coder_label_differs_from_each_sampled_primary_label=true` означает только то, что единая нормализованная ожидаемая метка отличается от первичной метки у каждой выбранной записи. Карты `audited_field_differences` и `non_audited_content_differences` перечисляют по каждому кандидату только названия различающихся полей. В штатном пути обе карты разрешаются одним приватным `resolutions.jsonl`, а финализатор сам создаёт `adjudications.jsonl` только для различавшихся полей из `label`, `speaker`, `norm_edition_id`, `reading_family`, `relation`, `reasoning_to_outcome`, `alternative_grounds` и `remedy`. Отличия в `proposition`, основной `quote`, основном `quote_locator` и `material_facts` требуют явного решения в том же `resolutions.jsonl`, но не превращаются в арбитражные записи восьмиполевого reliability-контракта. Ручное раздельное разрешение остаётся лишь экспертным совместимым путём без штатной квитанции финализации.

`audit-decisions.jsonl` сохраняет порядок `required_candidate_ids`, чтобы следующий этап получил замороженную выборку в ожидаемом порядке. Отдельная коллекционная контрольная сумма `secondary_coding_sha256` не зависит от порядка строк возвращённого файла: сначала полные вторичные записи сортируются по канонической контрольной сумме каждой записи, затем хешируется канонический массив. Это не меняет индивидуальный `secondary_coding_sha256` внутри каждого четырёхполевого решения.

Штатное закрытие обеих карт выполняет `quality coding-audit-finalize`. Команда принимает точный пакет и точный двухфайловый каталог импорта, а также два отдельно сохранённых SHA из успешно завершившихся `coding-audit-prepare` и `coding-audit-review-import`. Если есть различия, она требует один закрытый `resolutions.jsonl`: ровно одна строка на затронутого кандидата, точная привязка к квитанции и обеим разметкам и по одному выбору `primary`, `secondary` или типизированному `custom` на каждое различавшееся поле. Этот чувствительный файл должен быть соседом трёх каталогов под тем же приватным родителем, принадлежать эффективному пользователю, иметь режим `0600`, единственную жёсткую ссылку и на macOS не иметь расширенного ACL. Пропуск даёт неполный результат с кодом `3`; лишняя, дублированная, неоднозначная или неверно связанная запись даёт код `2`.

Финализатор сам реконструирует итоговые записи, создаёт совместимые `adjudications.jsonl`, заново рассчитывает `coding-reliability.json` и повторно проверяет буквальное и нормализованное присутствие основной и всех вложенных в `alternative_grounds` цитат в точном тексте соответствующего кандидата. Он атомарно публикует ещё `resolved-review-decisions.jsonl` и самохешируемую `coding-audit-finalization-receipt.json`. Контрольную сумму последней квитанции нужно брать только из полного stdout успешной команды и хранить вне итогового каталога; самохеш внутри проверяемого файла не заменяет внешний якорь. Квитанция не раскрывает тексты, цитаты, выбранные значения, метки людей, связанные с человеком времена или абсолютные пути. `quote_locator_review_declared=true` означает только декларацию человека; `quote_locator_verified=false` остаётся неизменным, потому что свободный локатор машинно не доказывается.

Последующее использование в тезисе требует проверяемую связь обоих точных файлов и отдельно сохранённого внешнего SHA. `uncertainty-profile` записывает закрытую проекцию происхождения и три точные хеш-привязки; проверенный пакет передачи содержит шесть привязок качества, причём только привязка квитанции имеет отдельное поле `expected_receipt_sha256`; `result import` принимает тот же SHA ещё одним независимым параметром командной строки. Одиночный `coding-reliability complete=true` остаётся `compatibility_only`. Потерянный либо сомнительный внешний SHA нельзя восстанавливать из квитанции: нужен штатный повтор финализации в новую соседнюю папку с неизменёнными входами и побайтным сравнением.

Точная проверка цитаты подтверждает только её буквальное присутствие в связанном тексте: она не подтверждает правильность формулировок, фактов, рассуждения, локатора или юридического вывода. Допустимый `norm_edition_id` не доказывает применимость редакции во времени. Закреплённое единое значение поля `coder` второго кодировщика и его отличие от первичного — проверка строк, а не аутентификация личности или доказательство независимой работы. Собственная контрольная сумма не аутентифицирует квитанцию; совпадение манифеста с отдельно сохранённым ожидаемым значением обнаруживает изменение относительно этого значения, но не доказывает авторство или происхождение рабочего каталога.

Ни каталог, ни ZIP, ни успешная квитанция не являются доказательством согласия кодировщиков, личности или независимости проверяющего, правильности локатора, фактов, нормы или юридического вывода, юридическим одобрением, разрешением на публикацию, проверкой актуальности права/практики или готовностью к подаче. Код `0` финализатора подтверждает только техническую полноту, точные связи, ограниченные текстовые проверки и атомарную публикацию. Ручные `coding-audit-plan`, четырёхполевые решения и отдельная `coding-reliability` остаются совместимы как экспертный путь, но не получают штатную квитанцию финализации. Команды принимают только строгий UTF-8 JSON/JSONL без повторных ключей на любом уровне и без `NaN`/бесконечностей. Одиночный суррогат Юникода в экранированном виде не становится доказательством: запись остаётся невалидной и получает только безопасный служебный отпечаток для диагностики.

Первый `analyze` создаёт measurements, пустой `thesis-candidates.jsonl` и шаблон общего `adverse-review.json`. Кандидаты появляются только после `review --decision evidence_reviewed` с завершёнными adverse/coverage review и повторного `analyze`.

## 3. Applicant-relative workbench

| Артефакт | Назначение | Gate |
|---|---|---|
| `position-cards.jsonl` | Полные одобренные карточки кассационных позиций | comparison |
| `comparability-matrix.jsonl` | Текущее сравнение каждой карточки с fingerprint | relation |
| `case-comparison.json` | Удобная копия последнего сравнения, не самостоятельный источник правды | relation |
| `applicant-position.json` | Проверенная классификация reading families со стороны заявителя | relation |
| `applicant-relations.jsonl` | `supports/adverse/distinguishes/neutral/unresolved` по каждой карточке | adverse |
| `review-queue.json` | Приоритет и все unresolved candidates без удаления | coding review |
| `case-adverse-review.json` | Четыре case-relative adverse buckets, query IDs, unresolved и claim effects | bridge |
| `normative-bridge.json` | Три звена, ordinary remedy, supporting/adverse cards и bounded wording | drafting ready |

Карточка позиции содержит полный `comparison_features[]`; текстовый label не заменяет структуру. Текущая строка comparison связывает:

- `fingerprint_sha256`;
- `applicant_features_sha256`;
- `candidate_features_sha256`;
- `position_card_sha256`;
- полученный из них и результата review `comparison_id`.

Relation дополнительно связывает `comparison_sha256` и `applicant_position_sha256`. Исправить карточку или fingerprint можно, но зависимая связь тогда перестаёт совпадать с текущим hash binding и не учитывается как approved. Новое review не должно маскировать факт stale-инвалидации.

Все состояния имеют значение: `matched`, `distinguishable`, `uncertain`; `approved`, `pending_human_review`; `supports`, `adverse`, `distinguishes`, `neutral`, `unresolved`; `stale=true/false`. Нельзя фильтровать незавершённые состояния из denominator или очереди только потому, что они не поддерживают тезис.

## 4. Approval, report и handoff

| Артефакт | Назначение |
|---|---|
| `human-decision.json` | Решение человека, привязанное к текущим plan/evidence hashes |
| `validation-report.json` | Состояние всех gates и хеши проверенного набора |
| `report/index.html` | Автономный локальный отчёт без внешних ресурсов |
| `report/manifest.json` | Hash binding отчёта к plan/evidence/fingerprint |
| `handoffs/*.json` | Content-bound envelope для соседнего скилла |
| `handoff-inbox.jsonl` | Атомарный идемпотентный ledger импортов |

Case-relative `drafting_ready` требует одновременно: готовый fingerprint; замороженный план; завершённые collection/coding/comparison/relation/adverse/coverage/analysis gates; валидный нормативный мост; human approval; текущие approval/validation hashes; кандидат, не превышающий `maximum_permitted_claim`.

Это всё ещё исследовательский gate. Для выпуска строки `practice_claim` центральный host отдельно связывает exact constitutional claim, native practice claim, selected issue, reviewed finding set, wording и ceiling; заново разрешает current result/refresh/approvals; и сверяет независимый полный draft index по [filing evidence binding](filing-evidence-binding.md). Handoff, локальный SHA и `drafting_ready=true` сами по себе release receipt не создают.

Default report всегда выводит открытые route и historical gaps, pending task counts, stale artifacts и точный denominator scope. Он раскрывает только текущие reviewed comparison/relation как findings, но сохраняет общий denominator карточек, чтобы положительные позиции не выглядели всем корпусом.

## 5. Временной контракт

`temporal_strata` и `interpretive_events` в плане необязательны. Если они заданы, страты непрерывно и без пересечений покрывают период; событие связывает соседние страты, а `effective_date` совпадает с началом следующей и подтверждается официальной ссылкой. Поля входят в SHA-256 плана.

`analysis.json` сохраняет `reading_family_by_year`, `reading_family_by_stratum`, `interpretive_event_findings`, `temporal_unassigned_chain_ids`, `temporal_analysis_complete` и `denominator_scope`. Знаменатель ячейки — только `approved_independent_coded_chains`; нулевая страта остаётся видимой.

`emergent_reading_candidate` означает впервые наблюдаемую после события новую семью без смешанного постсобытийного массива. `mixed_post_event` означает совместное наблюдение прежней и новой семей. Пробел enumeration, пустая сторона, неназначенная дата или неодобренная сопоставимость дают `insufficient_temporal_evidence`, а не тезис о динамике.

## 6. Стабильные идентификаторы и неизменяемость

- `plan_id`/`plan_sha256`: SHA-256 канонического frozen JSON без volatile-полей.
- `fingerprint_sha256`: SHA-256 нейтрального issue, norm refs и нормализованных features.
- `source_id`: SHA-256 роли источника и канонического URL.
- `snapshot_id`: SHA-256 raw bytes.
- `document_id`: SHA-256 нормализованного текста, иначе raw bytes.
- `chain_id`: официальный `host + case_uid`; fallback — `host + case_id + delo_id + new`; неуверенная связь получает `needs_merge_split_review`.
- `coding_id`: SHA-256 chain/document, codebook version и revision.
- `comparison_id`: content-derived ID текущего fingerprint, карточки, признаков и review provenance.

Frozen plan, versioned fingerprint, raw snapshot, run pins, treatment review history и handoff не переписываются. Исправление создаёт новую версию или новую content-bound запись. Текущие реестры comparison/relation могут заменять строку по `position_card_id`, но gate принимает её только при совпадении всех сохранённых хешей.

## 7. Handoff envelope

Минимальные поля: `schema_version`, `handoff_id`, `created_at`, `source_skill`, `target_skill`, `run_id`, `plan_sha256`, `evidence_sha256`, `payload_type`, `payload`, `limitations`. Для reviewed payload также обязателен текущий fingerprint binding.

Типы:

- `unproven_research_questions` — только вопросы и ограничения, без findings или complaint wording;
- `approved_bounded_findings` — drafting-ready bounded findings, supporting IDs, явный adverse list и `maximum_permitted_claim`;
- `authority_cards` — проверенные карточки, reviewer, `review_state=approved` и максимум вывода.

Legacy `selected_authorities` допускается только при чтении старого envelope. Повторная передача того же `handoff_id` идемпотентна. Проверка возвращает `valid`, `stale`, `tampered` или `incompatible`; ошибка импорта не изменяет corpus, approval или inbox.
