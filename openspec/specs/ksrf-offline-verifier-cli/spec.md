## Requirements
### Requirement: Offline verifier accepts only its declared command grammar

The directly executable offline verifier MUST accept an empty argument list or
exactly one help flag, `-h` or `--help`. It MUST reject every other argument
sequence, including unknown options, positional values, option abbreviations,
an exact help flag combined with another token, and invented target-selection
options. Rejection MUST occur before the offline validation policy reads or
enumerates the skills filesystem. It MUST exit with code `2`, write the usage
error to stderr, keep stdout empty, and MUST NOT print a successful or failed
verification result. Direct execution MUST NOT create bytecode or another
artifact in the installed skill while handling arguments or importing its
bundled policy.

#### Scenario: Misspelled option is rejected

- **WHEN** a user invokes the verifier with `--strcit`
- **THEN** the command exits `2` on stderr before validation and does not claim
  that offline self-containment was verified

#### Scenario: Positional value is rejected

- **WHEN** a user supplies a positional token to the verifier
- **THEN** the command exits `2` before validation instead of silently ignoring
  the token

#### Scenario: Invented target option is rejected

- **WHEN** a user supplies `--skills-root` and a path
- **THEN** the command exits `2` before validation and does not imply that the
  named path was inspected

#### Scenario: Help cannot hide another invalid token

- **WHEN** `-h` or `--help` is combined with any additional argument
- **THEN** the complete sequence is rejected with code `2` before validation

### Requirement: Offline verifier help is side-effect-free and Russian

An exact `-h` or `--help` request MUST print concise Russian command guidance to
stdout, exit `0`, and complete before validation or skill-directory
enumeration. The guidance MUST state that direct execution checks the installed
set containing the script and MUST route explicit-target verification to
`install.sh --verify --target PATH`. It MUST NOT print a verification success
or failure result or mutate the installed runtime tree.

#### Scenario: Long help is requested

- **WHEN** a user invokes the verifier with exactly `--help`
- **THEN** Russian guidance is printed on stdout with code `0`, stderr remains
  empty, and no validation scan runs

#### Scenario: Short help is requested

- **WHEN** a user invokes the verifier with exactly `-h`
- **THEN** it has the same no-scan help semantics as `--help`

### Requirement: No-argument offline verification remains compatible

An empty argument list MUST preserve the verifier's self-relative skills root,
offline policy, importable function API, stdout rendering, and return codes.
The existing success result MUST remain code `0`; validation findings MUST
remain code `1`. Direct execution MUST NOT gain an arbitrary target option or
claim the stronger repository-side preflight/postflight trust boundary, and it
MUST NOT dirty the installed runtime tree with generated bytecode.

#### Scenario: Installed verifier runs without arguments

- **WHEN** the bundled verifier is executed without arguments from any working
  directory
- **THEN** it validates the installed skillset containing its own script and
  preserves the established verification result and exit semantics
