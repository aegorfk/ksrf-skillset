## Context

Каноническая рабочая копия четырнадцати KSRF-скиллов находится в `~/.codex/skills`, а публичная поставка — в `aegorfk/ksrf-skillset`. Существующие `sync_global_skills.sh` и `install.sh` используют `rsync --delete`, поэтому устаревший checkout опасен в обоих направлениях. Текущий манифест проверяет дерево скиллов, но сам по себе не доказывает, что checkout чист, его HEAD опубликован в live `main`, а сеть действительно подтвердила SHA.

## Goals / Non-Goals

**Goals:**

- Сделать публикацию обязательной частью завершения любого изменения skillset.
- Разрешать перезапись глобальных скиллов только из чистого checkout, точный HEAD которого совпадает с live `refs/heads/main` ожидаемого публичного репозитория.
- Fail closed при недоступной сети, неожиданном remote, грязном checkout, расхождении SHA или дерева с манифестом.
- Сохранить безопасную установку в явно заданный отдельный каталог для тестов.
- Дать воспроизводимый release workflow и точный отчёт при блокере.

**Non-Goals:**

- Автоматически коммитить или отправлять изменения без отдельного release-действия агента.
- Менять содержимое четырнадцати KSRF-скиллов.
- Заменять юридические и поведенческие проверки скиллов.
- Разрешать публикацию непроверенной кандидатной версии напрямую в stable.

## Decisions

1. **Проверять live `origin/main`, а не только локальный tracking ref.** Guard вызывает `git ls-remote origin refs/heads/main`, проверяет ожидаемый GitHub remote и сравнивает live SHA с `HEAD`. Альтернатива — `origin/main` — отвергнута, потому что tracking ref может быть устаревшим.
2. **Глобальная установка fail closed.** Перед записью в канонический `${CODEX_HOME:-$HOME/.codex}/skills` установщик требует чистый checkout, live SHA и актуальный manifest. Явный нестандартный `--target` остаётся clean-room режимом и не перезаписывает рабочие глобальные скиллы. Оба режима вызывают один Python copier и единый exclusion contract; широкие цели, symlink и не-каталоги отклоняются до записи.
3. **Синхронизация начинается только от актуального чистого `origin/main`.** До копирования глобальных скиллов в репозиторий sync-скрипт запускает preflight, валидирует exact active allowlist зеркальных tools, а после копирования регенерирует манифест с проверенным base SHA. Retired mirrors удаляются только по отдельному явному allowlist. Это предотвращает сборку release поверх чужих, устаревших или молча оставшихся файлов.
4. **Завершённость определяется удалённым SHA.** После commit/push агент обязан повторно получить live SHA и подтвердить его равенство локальному HEAD. Локальный commit без push остаётся незавершённым.
5. **Политика и автоматическая проверка разделены.** `AGENTS.md` задаёт обязательства для агентов; `docs/PUBLICATION_CONTRACT.md` — операторский протокол; Python guard реализует проверяемые инварианты без внешних зависимостей.
6. **Manifest покрывает payload и release-tools.** Schema 1.2 хранит digest точного allowlisted дерева 14 скиллов и каждого исполняемого release-tool. Сам manifest не хэширует себя; чистый HEAD, равный live main, связывает его и остальные versioned-файлы. `remote_base_commit` — полный 40-hex SHA начала sync, который должен существовать и точно равняться первому родителю release HEAD. Так один manifest соответствует ровно одному atomic release commit.

## Risks / Trade-offs

- **[GitHub или сеть недоступны]** → глобальная установка и release-preflight блокируются; допускается только clean-room установка, а в отчёте фиксируется точный непубликованный манифест.
- **[Remote использует допустимый иной синтаксис URL]** → guard нормализует SSH/HTTPS формы только для ожидаемого owner/repo и отклоняет остальные.
- **[Легитимная установка из тега]** → глобальная запись всё равно блокируется, пока этот commit не является live `main`; это сознательный stable-only контракт.
- **[Manifest устарел]** → глобальная установка блокируется до его регенерации и публикации вместе с release.

## Migration Plan

1. Опубликовать policy, guard и изменения shell-скриптов одним атомарным commit в `main`.
2. Проверить live remote SHA после push.
3. После этого использовать guard для всех следующих синхронизаций и глобальных установок.
4. Для отката вернуть `main` отдельным revert-коммитом; не устанавливать локально отменённый SHA до его публикации и live-проверки.

## Open Questions

Нет блокирующих вопросов. Автоматическое открытие PR вместо прямого атомарного push может быть добавлено отдельно, не ослабляя требование live SHA.
