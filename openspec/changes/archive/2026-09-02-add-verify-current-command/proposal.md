# Proposal: add a short current-release verification command

## Problem

`./install.sh --status` теперь честно отделяет структурную проверку от проверки содержимого и выдаёт корректную команду runtime-валидатора. Но пользователю всё ещё приходится копировать длинный путь к Python и внутреннему скрипту. Кроме того, обычный код возврата валидатора сообщает только о качестве runtime-пакета: состояния `different` и `unknown` выводятся в отчёте, но сами по себе не дают ненулевой код для автоматизации.

## Change

- Добавить публичный режим `./install.sh --verify-current [--target ПУТЬ]`.
- Делегировать единственному repo-side runtime-валидатору с `--profile runtime --strict --check-updates --require-current`.
- Зафиксировать коды: `0` — runtime прошёл и `current`; `10` — runtime прошёл, но `different`; `20` — runtime прошёл, но freshness `unknown`; прежние `1` и `2` сохраняют значение validation/usage failure.
- Оставить `--status` офлайн и заменить его длинную рекомендацию короткой shell-командой для точной целевой папки.
- Сохранить прежнее поведение обычной установки, статусную JSON-схему и внутренний runtime JSON-отчёт; публичный короткий режим использует однозначные коды без новой машинной схемы для preflight-ошибок.

## User value

Проверка актуальности становится одной запоминаемой командой. Человек получает русское объяснение, а автоматизация может отличить подтверждённое совпадение, известное отличие и неполную сетевую проверку без разбора текста.

## Non-goals

- Не доказывать происхождение установленной копии.
- Не проверять актуальность права, практики или готовность жалобы к подаче.
- Не устанавливать обновление автоматически.
- Не включать `tests/`, `evals/`, OpenSpec или release-инструменты в пользовательский runtime.
