## Context

Canonical `install.sh` запускает publication verifier до writer. После прошлого
изменения его успешный stdout скрыт, но ненулевой результат всё ещё пропускает
сырой stderr прямого maintainer CLI. Такой stderr может содержать английский
текст, локальные пути, remote URL, SHA, фрагмент `git status` или внутреннее имя
проверки. Прямой CLI обязан сохранить эти данные для диагностики, публичная
обёртка — нет.

## Goals / Non-Goals

**Goals:**

- выводить при отказе canonical-установки только фиксированное русское
  объяснение, отсутствие записи и действие;
- подавлять произвольные stdout/stderr вложенного verifier;
- сохранять точный числовой ненулевой статус и fail-before-writer;
- не менять прямой maintainer CLI, JSON, sync-route и non-canonical install.

**Non-Goals:**

- классифицировать внутреннюю причину отказа в публичном интерфейсе;
- менять publication policy, Git/network-вызовы или transaction writer;
- локализовать прямой maintainer CLI;
- добавлять новый флаг подробности.

## Decisions

1. Canonical shell-ветка запускает verifier в условии `if` с обоими потоками,
   направленными в `/dev/null`. В `else` немедленно сохраняется `$?`, печатаются
   две фиксированные строки через `printf` в stderr и выполняется `exit` с тем же
   статусом. Ошибка записи самого сообщения нейтрализуется `|| :`, чтобы закрытый
   stderr не подменил исходный статус guard. Команда в условии совместима с
   `set -e` и macOS Bash 3.2.
2. Сообщение не интерполирует exception, repo, target, remote, SHA или stdout/
   stderr verifier. Оно честно говорит, что опубликованный выпуск подтвердить не
   удалось, навыки не изменены, и предлагает обновить локальную копию и открыть
   README для технической диагностики.
3. Подробности не захватываются во временный файл и не сохраняются: это избегает
   новых секретных/runtime-артефактов и лимитов чтения. Maintainer повторяет
   прямую команду из README.
4. Регрессия использует verifier, который пишет разные секретные значения и в
   stdout, и в stderr, затем возвращает нестандартный код `7`. Тест требует
   точный фиксированный stderr, пустой stdout, код `7` и отсутствие writer.
5. Отдельные regressions проверяют signal-status `143` без Bash-диагностики и
   сохранение кода `7`, даже когда публичный stderr заранее закрыт.
6. Отдельный unit-тест фиксирует, что прямой verifier по-прежнему возвращает
   подробный stderr при `PublicationStateError`.

## Risks / Trade-offs

- [Публичное сообщение не называет конкретную техническую причину] → одна
  безопасная рекомендация подходит всем отказам, а точный direct CLI указан в
  README.
- [Будущий verifier начнёт писать важную ошибку только в stdout] → public wrapper
  всё равно fail-closed и не раскрывает её; direct CLI остаётся источником
  диагностики.
- [Ненулевой статус выходит за обычные 1/2] → wrapper передаёт любой фактический
  числовой статус без переклассификации; regression закрепляет код `7`.

## Migration Plan

Миграции данных нет. Выпуск проходит обычный manifest-bound pipeline. Откат
возвращает прежнюю прямую передачу stderr, не затрагивая установленный runtime.
