## Context

Для канонической цели `install.sh` сначала запускает
`tools/verify_publication_state.py`. Прямой CLI намеренно печатает подробное
доказательство публикации для сопровождающего, но shell-обёртка без изменений
передаёт эту строку обычному пользователю. Затем Python-установщик уже печатает
русское сообщение об успешной транзакции.

## Goals / Non-Goals

**Goals:**

- оставить в обычном успешном stdout только понятный русский результат и
  `KSRF_SKILLS_ROOT`;
- сохранить publication guard обязательным и fail-closed до любой записи;
- сохранить прямой подробный maintainer-интерфейс без изменений;
- закрепить разделение регрессионными shell-тестами.

**Non-Goals:**

- менять состав runtime, транзакцию, манифест или сетевой протокол;
- добавлять новый пользовательский флаг подробности;
- менять stdout/JSON прямого `verify_publication_state.py`;
- локализовать в этой теме все возможные maintainer-ошибки guard.

## Decisions

1. `install.sh` подавляет только успешный stdout вложенного publication guard в
   канонической ветке. Его stderr и код выхода не перенаправляются, поэтому
   `set -e` по-прежнему останавливает установку до запуска writer.
2. Новый флаг не вводится: подробный вывод уже доступен через прямой
   `python3 tools/verify_publication_state.py --repo .` и через его `--json`.
   `tools/sync_global_skills.sh` продолжает пользоваться этим maintainer-
   интерфейсом напрямую.
3. Shell-регрессии используют временный checkout с детерминированными fake
   guard/installer, чтобы проверить разделение вывода без сети и без изменения
   настоящей глобальной установки.
4. README рядом с обязательной публикацией называет прямой maintainer-маршрут,
   а раздел установки описывает только пользовательский результат.
5. Существующее обещание совместимости offline-режима уточняется отдельным
   delta: `--status`, `--verify` и `--verify-current` не меняются, а у обычной
   установки меняется только успешный stdout, явно заданный transaction-spec.

## Risks / Trade-offs

- [Подавление stdout может скрыть будущую диагностическую строку guard] → прямой
  CLI остаётся источником подробностей, а failure stderr и код выхода не
  подавляются.
- [Shell-обёртка может случайно продолжить работу после отказа guard] → отдельный
  тест требует ненулевой код, отсутствие вызова installer, сообщения об успехе
  и `export`.
- [Тест может зависеть от GitHub] → fake-компоненты проверяют только контракт
  композиции stdout/exit без сети.

## Migration Plan

Изменение не требует миграции данных. После тестов и strict OpenSpec QA оно
публикуется обычным manifest-bound выпуском; откат — возврат одной строки
перенаправления в shell-обёртке.
