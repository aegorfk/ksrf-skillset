## Контекст

`validate_authority_ledger.py` намеренно не приводит входные значения к строкам:
`require_string` добавляет диагностическую ошибку, но `validate_transfer` сохраняет
исходный словарь для последующих проверок. Почти все проверки уже работают с
типобезопасными значениями, однако проверка непустого transfer-limit обращалась к
исходному словарю напрямую.

## Решение

В `Validator.validate_authorities` сначала получить исходное `limit`, а в
`drafting_ready` ветке вызывать `.strip()` только после явной проверки
`isinstance(..., str)`. Типовая диагностика остаётся в `validate_transfer`; числа,
контейнеры и `null` не коэрсятся в текст. Валидные строки и пустые строки
сохраняют текущую семантику.

CLI уже возвращает `1` после `validator.validate` и печатает накопленные ошибки;
дополнительный широкий `except` не нужен и не должен скрывать ошибки программирования.

## Границы и риски

- Guard не расширяется на другие поля: это отдельные гипотезы.
- Числа, boolean, `null`, массивы и объекты не коэрсятся в текст.
- При ошибке не создаются и не изменяются файлы: validator только читает вход.
- Тест запускает standalone CLI офлайн, без внешних сервисов.

## Проверка

1. Красный probe на родительском commit должен показать `AttributeError` для
   `transfer.limit=[]`.
2. TDD-тест проверяет пять контейнерных/числовых вариантов и валидную строку.
3. Запустить focused suite, полный набор релевантных KSRF тестов, strict/offline
   проверки и `openspec validate --all`.
